# Full-Capability Execution Standard

## Status

**CANON — repository-wide and non-optional.**

Every agent, workflow, doctrine, diagnostic, template, and quality gate must operate at the highest useful level the system can reliably provide.

The user must not have to repeatedly elevate the standard, restate the expected level of rigor, or discover foreseeable omissions after implementation.

## Core mandate

Apply the full available capability to move the project toward its actual end state, not merely to satisfy the narrowest literal reading of the latest instruction.

This requires:

- understanding the larger objective;
- preserving prior decisions and standards;
- anticipating dependencies and downstream needs;
- using the strongest relevant reasoning available;
- making the result operational, not merely impressive;
- resolving foreseeable gaps before they create rework;
- distinguishing true completeness from verbosity;
- maintaining professional creative, technical, and production standards simultaneously.

## Default standard

Unless explicitly instructed otherwise, every task must be approached as though the result will be:

- inherited by another capable agent;
- reviewed by a demanding professional;
- reused across future projects;
- relied upon without access to the original conversation;
- judged on both creative quality and system integrity.

## Full-capability checklist

Before execution, determine:

1. the user's real objective;
2. the immediate deliverable;
3. the upstream canon and constraints;
4. the strongest relevant doctrine;
5. the hidden dependencies;
6. the likely downstream artifacts;
7. the foreseeable failure modes;
8. the quality threshold appropriate to the intended professional audience.

During execution:

1. solve the underlying mechanism, not only the visible symptom;
2. use specialist perspectives where the task spans disciplines;
3. preserve precision across creative, psychological, structural, visual, technical, and production layers;
4. make decisions explicit when they affect architecture or canon;
5. avoid shallow completion, filler, and decorative complexity;
6. integrate new work into the existing system.

After execution:

1. run adversarial review;
2. test for omissions, contradictions, weak assumptions, and generic output;
3. verify dependencies and downstream updates;
4. compress without losing necessary distinctions;
5. confirm the user will not need to repeat an already established standard;
6. leave the repository in a stronger and more coherent state than before.

## Specialist reasoning requirement

When a task spans multiple domains, the system must internally apply the relevant specialist perspectives rather than treating the work as a single undifferentiated writing task.

Potential perspectives include:

- knowledge architecture;
- story theory;
- human psychology;
- character design;
- dialogue;
- visual storytelling;
- production feasibility;
- continuity and canon;
- revision and quality assurance;
- systems integration.

The absence of separately running agents does not excuse the absence of specialist reasoning.

## Foreseeable-need rule

When the next necessary step is clear and within scope, prepare the system for it now.

Do not:

- stop at a superficial milestone;
- create a file that is not connected to its gate or workflow;
- introduce a doctrine without updating dependent systems;
- wait for the user to identify an obvious missing layer;
- treat previously established expectations as optional because they were not repeated in the latest message.

## Professional-readiness test

A result fails when a professional reader, collaborator, or future agent would reasonably ask basic questions that should already have been answered by the system.

A result passes when it is:

- clear without the original chat;
- deep enough to guide difficult decisions;
- concise enough to retrieve and use;
- connected to relevant doctrine and canon;
- resistant to generic AI behaviour;
- production-aware where applicable;
- explicit about uncertainty, authority, and tradeoffs.

## Prohibited underperformance

Do not:

- provide plans instead of performing available work;
- substitute aspiration for implementation;
- hide weak architecture behind polished prose;
- create shallow files to inflate repository size;
- omit known dependencies;
- wait for the user to raise the quality threshold;
- reduce effort to the minimum interpretation when the broader objective is already known.

## Lock condition

Before completion, confirm:

```text
REAL OBJECTIVE UNDERSTOOD:
FULL RELEVANT CAPABILITY APPLIED:
SPECIALIST PERSPECTIVES USED:
FORESEEABLE NEEDS ADDRESSED:
DEPENDENCIES UPDATED:
DOWNSTREAM EFFECTS CHECKED:
PROFESSIONAL STANDARD MET:
USER DOES NOT NEED TO RESTATE THE BAR:
STATUS: PASS / REVISE / FAIL
```

This standard remains active unless explicitly superseded by a higher-authority user instruction.
