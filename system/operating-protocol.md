# Operating Protocol

## Purpose

This protocol turns an AI model into a repeatable story-development process. It prevents blank-page generation, canon drift, undiagnosed rewrites, foreseeable omissions, and endless taste-based iteration.

All work performed under this protocol must comply with `system/doctrine-design-standard.md`.

## Intake contract

Every task should resolve the following before substantial drafting:

- **Deliverable:** scene, outline, treatment, screenplay, bible, pitch, notes or research.
- **Audience:** creator, actor, producer, financier, department head or general viewer.
- **Format:** feature, short, vertical episode, series, prose or hybrid.
- **Stage:** discovery, architecture, drafting, diagnosis, revision or packaging.
- **Authority:** exploratory, proposed, approved or locked.
- **Constraints:** length, budget, location, cast, rating, culture, language and deadline.
- **Target effect:** what the audience should anticipate, feel, understand or question.
- **Dependencies:** which canon, doctrine, research, templates, and prior decisions govern the task.
- **Downstream impact:** which artifacts may need updating if the task changes story truth or system behaviour.

When information is missing, infer only what can be safely inferred and label it. Do not stall a task over details that can be resolved through a reversible proposal. Do not omit a material requirement merely because it was not named in the latest instruction when it is already established elsewhere.

## Development loop

### 1. Orient

Read the source hierarchy. Build a compact state model containing premise, protagonist, central pressure, controlling theme question, current structure, canon constraints, open decisions, and established user standards.

### 2. Diagnose

Name the actual problem before changing pages. Distinguish among premise, causality, agency, stakes, character, pacing, information, tone, dialogue, continuity, formatting, integration, and completeness defects.

### 3. Design

Generate no more than three materially different solutions. Evaluate each by dramatic power, originality, canon impact, setup cost, production cost, dependency impact, and downstream consequences.

### 4. Decide

Select or recommend one solution. Record any canon-changing choice. Do not blend incompatible options into a compromise that loses the purpose of both.

### 5. Execute

Draft at the requested level. Preserve uncertainty where the story benefits from uncertainty; remove uncertainty where the production team needs precision. Complete all material mechanisms required for reliable use.

### 6. Attack

Run an adversarial review. Ask what is generic, convenient, unearned, repetitive, over-explained, culturally unsupported, impossible to stage, under-specified, isolated, contradictory, or likely to create later rework.

### 7. Dependency scan

Before refinement, inspect:

- prerequisites changed by the work;
- workflows and gates that should invoke it;
- templates that need corresponding fields;
- indexes or navigation that must be updated;
- canon, continuity, character, mythology, timeline, or production documents affected;
- foreseeable edge cases not yet covered.

### 8. Refine

Revise the mechanism first, then the prose. A sentence-level pass cannot rescue a scene with no choice, pressure or turn. A formatting pass cannot rescue a doctrine with no diagnostic or repair logic.

### 9. Compress

Remove language that does not change understanding, execution, diagnosis, repair, or verification. Preserve all distinctions necessary to prevent error.

### 10. Lock

Mark accepted decisions, update continuity and dependencies, identify the next required action, and confirm the result meets all relevant acceptance gates and the doctrine design standard.

## Context loading rule

Load only the knowledge needed for the current task. More context is not automatically better. Prioritize high-authority, task-relevant files and summarize them into a working brief before reasoning. However, never omit a known governing standard or dependency merely to minimize context.

## Change control

A change is **local** when it affects wording or execution without changing story truth or system behaviour.

A change is **architectural** when it alters motive, causality, timeline, mythology, relationship, theme, reveal order, ending, workflow, quality threshold, source hierarchy, doctrine dependency, or agent responsibility.

Architectural changes require:

1. dependency scan;
2. downstream-impact scan;
3. decision-log entry;
4. updates to all directly affected files;
5. confirmation that no contradictory doctrine remains active.

## Foreseeable-gap review

Before declaring work complete, ask:

- What material question would the next agent still need answered?
- What could be misread by a competent but context-limited model?
- Which edge case could bypass the intended rule?
- Which existing artifact may now be stale?
- Which user instruction risks being lost in future turns?
- Is the result truly concise, or merely underdeveloped?
- Is the result truly detailed, or merely repetitive?

Resolve what can be resolved without inventing project canon.

## Failure recovery

When output feels "AI-written," do not simply request more grit, poetry or realism. Diagnose the cause:

- abstraction instead of observed detail;
- explanation instead of behavior;
- familiar beat sequencing;
- uniform sentence rhythm;
- no meaningful character resistance;
- no irreversible turn;
- borrowed genre shorthand;
- excessive completeness that removes negative space.

When a system artifact feels inadequate, diagnose whether it lacks:

- a complete mechanism;
- causal explanation;
- operational steps;
- failure modes;
- diagnostic questions;
- ordered repairs;
- acceptance tests;
- dependencies;
- downstream integration;
- sufficient concision for retrieval.

Repair the mechanism that caused the failure. Do not conceal it with polish, volume, or additional headings.
